# Анализ разработки плагина Logcat viewer
> Просмотр системного журнала Android внутри ExteraGram
> Источники: исходный код `Logcat_Viewer.plugin` и встроенная нативная библиотека `liblogcat_reader.so`

---

## Архитектура и принцип работы

Плагин состоит из двух частей:

- **Python-часть** — отвечает за интерфейс, хранение полученных записей, поиск, отображение статусов и просмотр полного сообщения.
- **Нативный модуль `liblogcat_reader.so`** — отвечает за чтение строк журнала через экспортируемые функции.

Нативная библиотека встроена непосредственно в исходный файл плагина в виде Base64-строки, сжатой через `zlib`. При запуске данные декодируются, распаковываются и записываются в каталог приложения, после чего библиотека загружается через `ctypes.CDLL`.

После загрузки вызываются функции `lv_start`, `lv_read_line` и `lv_stop`. Чтение выполняется в отдельном потоке, который получает строки от нативного модуля и передаёт их Python-части. Python разбирает записи, сохраняет их в памяти и отображает в настройках ExteraGram.

---

## Ключевые решения и нюансы

### 1. Встраивание нативной библиотеки

Библиотека хранится внутри `.plugin`, поэтому для установки не требуется отдельно размещать `liblogcat_reader.so` рядом с файлом плагина.

Встроенные данные ограничены маркерами:

```python
# EMBEDDED_NATIVE_BEGIN
...
# EMBEDDED_NATIVE_END
```

При запуске выполняется декодирование Base64 и распаковка `zlib`. Полученные байты записываются в файл `liblogcat_reader.so`.

Встроенный бинарный модуль собран для ARM64. Для другой архитектуры потребуется соответствующая сборка библиотеки.

---

### 2. Извлечение и загрузка `.so`

Плагин получает контекст приложения через `ApplicationLoader.applicationContext`. В качестве каталога для библиотеки сначала используется `getCodeCacheDir()`, а если получить этот путь не удаётся — `getFilesDir()`.

Внутри создаётся каталог `logcat_viewer_native`, куда записывается библиотека.

После этого выполняется загрузка:

```python
_READER = ctypes.CDLL(path)
```

Перед вызовом нативных функций Python задаёт типы аргументов и возвращаемых значений через `argtypes` и `restype`. Это необходимо для корректной передачи данных между Python и C-кодом.

Перед повторной записью проверяется размер уже существующего файла. Если размер совпадает с размером распакованных данных, запись пропускается. При этом контрольная сумма не проверяется, поэтому совпадение размеров не гарантирует идентичность содержимого.

---

### 3. Запуск нативного читателя

После загрузки библиотеки вызывается `lv_start()`. Если функция возвращает ненулевое значение, запуск считается неудачным, а интерфейс получает соответствующий статус.

При успешном запуске создаётся отдельный поток `LogcatViewerNative`, выполняющий `_reader_loop()`.

Внутри цикла вызывается `lv_read_line()` с буфером размером 65536 байт и тайм-аутом 500 мс. Положительный результат означает, что получена строка для обработки. Отрицательный результат переводит читатель в состояние остановки.

Успешная загрузка библиотеки и успешное получение записей — разные этапы. Сам факт загрузки `.so` не подтверждает, что нативный модуль действительно получает строки системного журнала.

---

### 4. Обработка полученных строк

Байты преобразуются в текст через UTF-8:

```python
buffer.value.decode("utf-8", "replace")
```

Режим `replace` позволяет продолжить обработку, даже если последовательность байтов содержит некорректные символы.

Далее `_add_line()` удаляет завершающие символы новой строки и пытается разобрать запись с помощью регулярного выражения `_LOG_RE`.

Если формат распознан, сохраняются:

- дата и время;
- PID и TID;
- уровень записи;
- тег;
- текст сообщения.

Время для интерфейса приводится к формату `дд-мм чч-мм-сс`.

Если строка не соответствует ожидаемому формату, она не отбрасывается: исходный текст сохраняется, а в качестве тега используется `logcat`. Это позволяет не терять записи только из-за несовпадения формата.

---

### 5. Хранение записей и защита от переполнения

Для хранения используется список `_RECORDS`. Максимальное количество записей ограничено константой:

```python
_MAX_ROWS = 3000
```

При превышении лимита старые элементы удаляются, а последние записи сохраняются.

Это ограничивает объём данных в памяти при длительном чтении журнала. Записи не сохраняются в постоянный архив на диске: буфер существует в памяти процесса.

Для доступа к списку используется `threading.RLock`. Блокировка защищает добавление записей и получение копии списка от одновременного изменения из разных потоков.

---

### 6. Подавление повторов

Перед добавлением новой записи плагин проверяет последнюю сохранённую строку. Если её полный текст совпадает с новым и с момента предыдущей записи прошло менее секунды, новая запись пропускается.

Это не глобальное удаление дубликатов. Одинаковые сообщения, появившиеся позже или между другими сообщениями, сохраняются. Такой механизм предназначен только для подавления ближайших повторов.

---

### 7. Поиск по тегу и тексту

Поисковый запрос хранится в настройке `search`. Перед фильтрацией он очищается от пробелов по краям и переводится в нижний регистр.

Проверяются три поля:

- тег записи;
- текст сообщения;
- полная исходная строка.

Поиск работает как обычное совпадение подстроки без учёта регистра, а не как регулярное выражение.

Фильтрация выполняется при построении страницы настроек. Исходный список записей не изменяется, поэтому после очистки запроса снова становятся доступны все сохранённые записи.

Для отображения новых результатов интерфейс должен быть перестроен после подтверждения ввода поискового запроса. Само сохранение настройки не гарантирует автоматического обновления уже открытой страницы.

---

### 8. Обновление интерфейса

Кнопка «Обновить список» переключает значение `_refresh_token` и вызывает:

```python
self.set_setting(
    "_refresh_token",
    token,
    reload_settings=True
)
```

Переключение значения позволяет выполнить обновление даже тогда, когда кнопка нажимается повторно. Параметр `reload_settings=True` запрашивает перестроение страницы настроек.

При этом обновление интерфейса не очищает список и не перезапускает нативный читатель. Оно обновляет отображение уже собранных записей, а работающий поток продолжает получать новые строки.

---

### 9. Просмотр полной записи

Основной список отображает текст сообщения и краткую метаинформацию: время, PID, TID, тег и уровень, если он распознан.

При нажатии на запись открывается `BottomSheet`, внутри которого показывается полная исходная строка. Для текста используется моноширинный шрифт, а выделение включено, чтобы пользователь мог копировать содержимое.

Такой подход позволяет сохранить основной список компактным, не лишая пользователя доступа к исходной записи целиком.

---

### 10. Логирование самого плагина

Для отправки собственных сообщений используется механизм логирования ExteraGram через `android_utils.log`.

Плагин может записывать события загрузки, запуска нативного читателя, обновления списка, выгрузки и возникающих ошибок. Эти сообщения предназначены для диагностики самого плагина.

Однако наличие вызова логирования не гарантирует, что собственные сообщения будут доступны внутри отображаемого списка: это зависит от того, какие записи фактически возвращает нативный читатель. Наличие или отсутствие таких сообщений следует оценивать по реальному результату работы на устройстве.

---

### 11. Статусы и обработка ошибок

Переменная `_STATUS` хранит состояние читателя. Она используется для отображения информации о загрузке нативного модуля, запуске чтения, остановке и возникших ошибках.

Ошибки при загрузке библиотеки, запуске или чтении переводятся в соответствующий статус. Некоторые ошибки также отправляются в системный журнал.

Сообщение о возможных ограничениях доступа к logcat является диагностической подсказкой, а не доказательством конкретной причины сбоя. Для установления причины необходимо учитывать фактический результат запуска и наличие полученных строк.

---

### 12. Остановка при выгрузке плагина

При выгрузке вызывается `_stop_reader()`. Функция устанавливает событие `_STOP` и вызывает `lv_stop()` у нативного модуля, если он загружен.

Событие сообщает Python-циклу о необходимости завершить работу, а `lv_stop()` передаёт команду остановки нативной стороне.

Это необходимо для корректного завершения работы читателя при отключении плагина. Фактическое время завершения зависит от реализации нативной функции и состояния чтения в момент остановки.

## Общая схема работы

```text
on_plugin_load()
    │
    ▼
_extract_native()
    │
    ├── декодирование Base64
    ├── распаковка zlib
    ├── выбор каталога приложения
    └── запись liblogcat_reader.so
            │
            ▼
       ctypes.CDLL()
            │
            ▼
         lv_start()
            │
            ▼
     поток LogcatViewerNative
            │
            ▼
       lv_read_line()
            │
            ▼
         _add_line()
            │
            ├── разбор строки
            ├── подавление ближайшего повтора
            ├── добавление в _RECORDS
            └── ограничение буфера до 3000 записей

create_settings()
    │
    ▼
     _viewer()
    │
    ├── получение поискового запроса
    ├── получение записей
    ├── фильтрация
    └── построение списка
            │
            └── нажатие → BottomSheet с полной записью

on_plugin_unload()
    │
    ▼
 _stop_reader()
    │
    ├── установка _STOP
    └── вызов lv_stop()
```

---

## Важные особенности

- Нативная библиотека встроена в файл плагина и извлекается при запуске.
- Бинарный модуль рассчитан на ARM64.
- Чтение журнала выполняется отдельным потоком, а интерфейс отвечает за отображение и фильтрацию.
- В памяти хранится не более 3000 записей; постоянный архив не создаётся.
- Поиск фильтрует уже полученные записи и не меняет сам поток logcat.
- Проверка размера существующей библиотеки не заменяет проверку контрольной суммы.
- Успешная загрузка `.so` не гарантирует успешного чтения системного журнала.
- Доступность конкретных записей, включая сообщения самого плагина, определяется фактическим выводом нативного читателя на устройстве.
